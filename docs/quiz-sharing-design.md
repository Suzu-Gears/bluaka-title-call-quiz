# 自作クイズ「作って公開」方式 設計書

自作クイズを URL だけで共有・プレイできる仕組みの全体設計。
第1弾(実装済み)の「生徒セット共有」に続き、**問題を1問ずつ手作りして公開する方式**
(衣装マッチング・可変択数・こだわりの誤答選択肢)を第2弾として設計する。

- 対象ブランチ: `claude/quiz-creation-sharing-4n8jm3`
- 状態: 第1弾 実装済み / 第2弾 本書は設計のみ

---

## 1. 目的と方針

### 1-1. なぜ「作って公開」方式か

自動生成(ランダム出題)は手軽だが、次のような「作者の意図」が乗った問題は自動生成と
相性が悪い:

- **似ている声だけを集めた選択肢**(同じ声優・似た声質・姉妹キャラ)
- **同じ生徒の別衣装をどれか当てさせる**(シロコ / シロコ（水着）/ シロコ＊テラー)
- 設問ごとに難易度を調整した**択数の変化**(自信のある問題は2択の引っ掛け、終盤は8択)

そこで「問題の中身は人間が作る。アプリは**再生・採点・共有**だけを担う」方式にする。
作者の作った問題構成は固定で共有され、ただし**出題音声は挑むたびに変わる**(後述)ため、
繰り返し遊べる。

### 1-2. 全体像

```
[作成者]                                [挑戦者]
クイズエディタで問題を作る                共有URLを開く
  │  問題リスト(形式・正解・選択肢)         │  URLハッシュから定義を復元
  ▼                                      ▼
定義をURLハッシュにエンコード ──共有──▶ 挑戦状バナー → プレイ → リザルト
  (サーバー保存なし)                       │
                                         └─ 結果をSNSシェア(同じURL入り) ─▶ 次の挑戦者
```

サーバー・DB は使わない。定義は URL そのものに入っているため、URL が生きている限り
クイズも生きている(アプリの静的ホスティング構成を変えない)。

## 2. URL 共有の原理(第1弾で実装済み・第2弾も同じ)

### 2-1. エンコードパイプライン

```
クイズ定義(JSON)
  → UTF-8 バイト列
  → deflate-raw 圧縮 (CompressionStream)
  → base64url
  → プレフィックス付与: "1."(deflate) / "0."(無圧縮フォールバック)
  → URL: https://…/#c=<エンコード済み文字列>
```

- 実装: `src/lib/quizShare.ts` (`encodeSharedQuizPayload` / `decodeSharedQuizPayload`)
- ハッシュ(`#`)に載せるためサーバーやアクセスログに定義が渡らない。PWA・オフラインでも動く
- `CompressionStream` 非対応環境(ほぼ無い)は `0.` プレフィックスの無圧縮にフォールバック
- デコード側はプレフィックスで分岐するため、新旧どちらの形式も読める

### 2-2. 容量の実測値

v2 形式(後述)のサンプルで実測した URL 長(ドメイン部含む概算):

| 問題数 | URL 長        |
| ------ | ------------- |
| 10問   | 約 340 文字   |
| 20問   | 約 430 文字   |
| 50問   | 約 750 文字   |
| 100問  | 約 1,300 文字 |

ブラウザ・チャットアプリで安全に扱える目安の 2,000 文字に対して十分な余裕がある。
X(Twitter) は URL を t.co に短縮するため文字数消費は一定。**上限は 100 問**とする
(それ以上はまず作らないが、超えたら生成時にエラー表示)。

### 2-3. セキュリティ

URL 由来の定義は**信頼しない入力**として扱う(第1弾で実装済みのパターンを踏襲):

- スキーマ検証: 型・上限(タイトル40文字・問題数100など)・不正値の除去を通ったものだけ採用
- 生徒 ID は手元の `final.json` に存在するものだけ有効。存在しない ID の問題はスキップ
- 表示はすべて `textContent` 経由(HTML を組み立てない)
- 定義から外部リソースを fetch しない(ID → 手元のアセットの解決のみ)

## 3. データモデル

### 3-1. バージョニング

| v   | 内容                             | 状態     |
| --- | -------------------------------- | -------- |
| 1   | 生徒セット共有(ids から自動出題) | 実装済み |
| 2   | 問題単位の手作り定義(本書)       | 設計     |

デコーダは `v` で分岐する。v1 の URL は今後も動き続ける(後方互換)。

### 3-2. v2 ペイロード

```jsonc
{
  "v": 2,
  "title": "似た声だけ集めた地獄の10問", // 40文字まで
  "author": "Suzu", // 任意・20文字まで(表示専用)
  "desc": "全部わかったら本物", // 任意・100文字まで
  "shuffle": false, // true なら出題順をシャッフル(既定: 作成順)
  "q": [
    // ── 択一(可変択数) ──
    // t:"c", a: 正解の生徒ID, o: 誤答の生徒ID(1〜7個 → 2〜8択)
    { "t": "c", "a": 10005, "o": [10008, 10012, 10031] }, // 4択
    { "t": "c", "a": 10005, "o": [10008] }, // 2択の引っ掛け

    // ── マッチング ──
    // t:"m", e: 対象の生徒ID(2〜6個)。全クリップを対象カードに割り当てる
    { "t": "m", "e": [10005, 20005, 30005] }, // シロコ3形態

    // ── 名前入力 ──
    // t:"i", a: 正解の生徒ID。lu: true でサジェスト無し(Lunatic)
    { "t": "i", "a": 10014 },
    { "t": "i", "a": 10014, "lu": true },

    // ── 音声固定(任意) ──
    // 既定は「挑むたびにランダム」。clip でクリップ名を固定できる(旧声優版の出題など)
    { "t": "c", "a": 10005, "o": [10008, 10012], "clip": "ch0184_title.g1" },
  ],
}
```

キーを1文字に切り詰めているのは URL 容量のため。deflate が繰り返しをよく圧縮するので、
問題数が増えても線形よりゆるやかにしか伸びない(実測は §2-2)。

### 3-3. 生徒 ID の扱い

- ID は `QuizEntry.PrimaryId`(別衣装は別エントリ・別 ID なので、衣装単位の出題がそのまま表現できる)
- 検証: 手元のデータに存在し、かつ `TitleCalls` が1本以上あるエントリのみ有効
- コラボ生徒の削除などで ID が消えた場合、その問題はスキップし
  「n 問は現在のデータで出題できないためスキップしました」と挑戦状バナーに注記する
  (1問も残らなければインポート自体をエラーにする)

## 4. クイズの形式

### 4-1. 択一(可変択数) `t:"c"`

- 正解1 + 誤答1〜7 = **2〜8択**。択数は問題ごとに自由
- 選択肢の並びは毎回シャッフル
- 出題音声: 正解生徒の最新世代クリップから**毎回ランダムに1本**
  (タイトルコールが複数ある生徒は、挑むたびに違う音声が流れる)。
  `clip` 指定があればそのクリップに固定
- UI は現行の4択とほぼ同じ(選択肢グリッドが 2〜8 に可変)。8択はスマホで 2列×4段
- 採点: 1問1点

### 4-2. マッチング `t:"m"`

「どの声がどの衣装(フォーム)か」を当てる形式。同一キャラの別衣装は別エントリなので、
エントリを 2〜6 個選ぶだけで成立する(別キャラ同士を混ぜてもよい)。

**プレイの流れ:**

1. 対象のカード(画像+名前)を N 枚並べて表示する
2. 1本目の音声が流れる → プレイヤーは「この声だと思うカード」をタップ
3. 割り当てたカードにはバッジ(♪1 など)が付き、次の音声が流れる
4. N 本すべて割り当てたら答え合わせ。正解のマッピングを表示し、
   各カードをタップすると対応する音声を聴き直せる

**仕様の要点:**

- 各エントリの音声は最新世代からランダムに1本ずつ(=ここも挑むたびに変わる)
- 音声の再生順はシャッフル
- 割り当てのやり直し: 答え合わせ前なら割り当て済みカードをタップで解除できる
- 採点: **全ペア正解で1点**(部分点なし)。リザルトには誤答ペアの内訳を表示
  - 部分点は集計とシェア文が複雑になるうえ、N=2 では意味がないため採用しない
- バリデーション: 全エントリが再生可能であること。名前が同一のエントリ同士は
  区別がつかないため混在を禁止(エディタ側で選択不可にする)

### 4-3. 名前入力 `t:"i"`

- 現行の名前入力と同じ判定(`normalizeQuizAnswer`: かな・全半角ゆれ吸収)
- `lu: true` でサジェスト無し(Lunatic)。問題単位で難易度を混ぜられる
- 出題音声のランダム再抽選は択一と同じ

### 4-4. 共通仕様

- 出題順: 作成順に固定(作者がストーリーを作れる)。`shuffle: true` で毎回シャッフル
- 進捗(習熟度)への記録: 択一・名前入力は現行どおり記録。
  マッチングは「エントリごとの正誤」をそのまま記録する
- リザルト・SNSシェア: 第1弾の仕組みをそのまま使う(スコア入りシェア文 + 挑戦URL +
  canvas スコアカード画像)。シェア文の「n/N問」の N は問題数

## 5. 作り方(クイズエディタ)

### 5-1. エディタ画面

「クイズを作って共有」ダイアログを**エディタ画面(全画面ビュー)**に拡張する。
構成:

```
[クイズ情報]  タイトル / 作者名 / 説明 / 出題順(固定・シャッフル)
[問題リスト]  ドラッグ(または▲▼)で並べ替え・複製・削除
  ├ 問題1: 択一   正解: シロコ        誤答: [シロコ＊テラー] [空崎ヒナ] (+追加)
  ├ 問題2: マッチ 対象: [シロコ] [シロコ（水着）] [シロコ＊テラー]
  └ 問題3: 入力   正解: 天童アリス   □Lunatic
[+ 問題を追加]  形式を選ぶ(択一 / マッチング / 名前入力)
[出力]  共有URLを作成 / JSONエクスポート / Xでシェア
```

**入力支援(作りやすさの核):**

- 生徒選択は検索ピッカー(かな検索対応・画像プレビュー・その場で音声試聴)
- 「同キャラの全フォームを追加」ボタン: 同じベース名のエントリを一括投入
  (マッチング問題が2タップで作れる)
- 「同じ声優の生徒」フィルタ: `CharacterVoice` で絞り込み、似た声の誤答集めを支援
- 音声固定トグル: 既定はランダム。固定したいときだけクリップを選ぶ

**下書き:** 編集内容は `localStorage`(`bluaka-title-call-quiz2.quiz-draft.v1`)に自動保存。
誤ってタブを閉じても復元できる。エクスポートした JSON を読み込んでも再編集できる
(共有 URL を貼り付けての再編集も可: デコード → エディタに展開)。

### 5-2. スプレッドシート/テキストからの一括作成

1行=1問のテキスト形式を受け付ける(第1弾の名前貼り付けの拡張)。
スプレッドシートで問題リストを管理している作者はコピペで取り込める:

```
択一, シロコ, シロコ＊テラー, 空崎ヒナ        ← 先頭が正解、以降が誤答(択数は列数で決まる)
マッチ, シロコ, シロコ（水着）, シロコ＊テラー
入力, 天童アリス
```

- 区切りはタブ/カンマ両対応(シートからのコピーはタブ区切りになる)
- 名前照合は第1弾の `matchPastedStudentNames` と同じ(ゆれ吸収・不明名は行ごとエラー表示)
- 逆方向(エディタ → この形式でコピー)も用意し、シートでの管理と往復できるようにする

### 5-3. 公開の形

- 基本は **共有URLがそのまま公開物**(第1弾と同じ)。X・LINE・Discord にURLを貼るだけ
- JSON エクスポートは「バックアップ・再編集・シート往復」用の中間形式
- 将来の拡張候補(本書のスコープ外):
  - 公開ギャラリー(要サーバー。GitHub の JSON リポジトリ + PR 受付でも代替可)
  - クイズごとの OGP 画像(要エッジ関数。URL だけでは OGP を変えられない)

## 6. プレイ側の挙動

1. URL を開く → `#c=` をデコード → スキーマ検証 → ID を手元データと突き合わせ
2. 挑戦状バナーに タイトル / 作者 / 問題数 / 形式の内訳(例: 択一6・マッチ3・入力1)を表示
3. 「挑戦する」で開始。問題ごとに形式に応じた UI を出し分ける
4. 全問終了でリザルト。シェア文には同じ挑戦 URL が入り、拡散ループが回る
5. スキップされた問題があれば挑戦前に注記(§3-3)

実装上は、現行 `quiz.ts` の「固定キュー出題」(`roundQueue`)を
「`QuestionPlan`(形式+正解+選択肢+クリップ)のキュー」に一般化する。
第1弾の挑戦状はこの上で「全問同形式・選択肢自動」の特殊ケースになるため、
v1/v2 のプレイ経路は統合できる。

## 8. 制約・注意点まとめ

- 問題数上限 100 / タイトル40字 / 説明100字 / 作者名20字 / 択数 2〜8 / マッチ対象 2〜6
- URL は定義そのもの: **URL を知っている人は誰でも遊べる**(限定公開の概念はない)
- データ更新でエントリが消えた問題はスキップ(全滅時のみエラー)
- マッチングに同名エントリの混在は不可(エディタで防止)
- 音声はランダム再抽選が既定のため、同じ URL でも毎回少し違う体験になる
  (固定したい問題だけ `clip` 指定)
